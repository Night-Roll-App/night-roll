# DK64 song pick — plan (2026-10-08)

Source: DK64 whole-album audit (Josh #216), open-items "N64 Rare: notes fade…" → "song-pick problems".
Rule that binds every step: CLAUDE.md "No one-time hacks in capture engines" — a game's identity may only
pick WHERE to look; what plays comes from the rip itself. A fix that needs to know "this is DK64" is a
warning plus an open-items entry, not a fix.

## The three problems (facts from the audit)

1. **Wrong song when the mini writes none of the RAM songs.** `miniRamSequence` (tools/n64/rare.mjs)
   ranks RAM songs by how many bytes the mini's own state chunk writes. If it writes none, it takes the
   first song by address. Result: `wrinkly-kong` gets the same .mid as `logo`, and `100-bananas` is Jungle
   Japes. The tags disagree with the captures: wrinkly-kong's tag says 80 s but the capture is 21.6 s;
   100-bananas' tag says 4 s but the capture is 124.8 s.
2. **Five identical Tag Barrel captures** (`tag-barrel-{donkey,diddy,lanky,tiny,chunky}`): 1022 notes,
   byte-identical .mid. The game mutes channels per Kong, and we don't read that mute. SM64's ducking
   has the same shape.
3. **Tag far longer than the capture, and not by a loop factor of 2:** mermaid-palace (tag 248 s,
   capture 66.6 s), fungi-forest-barrel-course (214 / 59.1), crystal-caves-earthquake (26 / 6.4),
   k-lumsy-key (14 / 3.7). This may be another wrong pick, or a capture that stops early.

## Step 0 — investigate before any code (report back, no fix yet)

For each of the 9 songs above:
- the RAM songs `findRamSequences` sees, as address, size and note count;
- what the mini's state overrides (`miniOverrideWords`, `miniOverrideRegs`);
- the tag `length`/`fade`;
- what lazyusf2 renders for the mini, as length and loudness envelope (tools/n64 already renders for
  the loudness work).

Then answer:
- (1) Does any generic signal in the rip pick the right RAM song? Candidates: tag length vs each song's
  own loop-free length; the lazyusf2 render's onset times vs each song's note-on times; a pointer word in
  the driver's state that holds the current sequence address.
- (2) Where does the driver keep a per-channel mute or enable mask? Look in the Rare driver state the
  rip writes (the mini chunks for the five barrels differ somewhere — diff them). Does the SM64 ducking
  work share a reader?
- (3) For the 4 short ones: wrong song, or early stop?

## Step 1 — fixes (only what Step 0 supports)

- **Pick:** when the mini writes none of the RAM songs, choose the song whose own evidence matches
  the mini. Prefer a driver pointer, since that is a fact. Otherwise match against the render. Use the
  tag length only as a tie-break. If no signal separates the songs, keep today's choice and add a
  louder warning in the capture.
- **Mutes:** read the per-channel mask from the rip's state and drop (or mark) muted channels. It must
  be generic: the same reader runs for every Rare-driver rip.
- **Short captures:** follow whatever Step 0 found.

## Tests

- tests/n64-rare.test.mjs: fixture-level unit tests for the pick and the mask reader, using the bytes
  that decide them (small text fixtures, no full rips).
- tests/n64-real.test.mjs: guarded by the local rip being present. Wrinkly Kong ≠ Logo, 100 Bananas ≠

- Re-capture DK64 through tools/recapture.mjs with the standing rule: beats moved → old song kept plus a
  "(re-capture)" copy; same beats → replaced. One push. Then loudness.
- Run the same dry run on the other Rare albums (DKR, Banjo, GoldenEye, JFG) to see what else the
  generic fix moves. Any change there is reported, not silently applied.
- Docs: NIGHT-ROLL.md N64 section; open-items closes the three audit lines.
- Ask tool: not applicable (capture pipeline, no user-facing control).

## Advisor review (2026-10-08) — REVISE; this section supersedes Step 0/1 where they differ

Findings, checked against /tmp/recap/rips/n64/donkey-kong-64:
- The tag-barrel minis write no ROM pages. They differ in GPR a0 (state offset 0x70): donkey 7,
  diddy 0xb, lanky 8, tiny 0xa, chunky 6. They also differ at 0x254 (CPU state) and in a few RDRAM
  words. wrinkly-kong has a0 = 0xab and 100-bananas a0 = 0xac, which look like song numbers.
  `rareSequenceOfSet`'s no-table branch (rare.mjs ~937) never calls `miniOverrideRegs`.
- The SM64 ducking reader (`duckedChannels`, capture.mjs) reads ROM pages these minis don't have,
  so it doesn't apply.
- measure-loudness renders our own pick, so it can't judge the pick. The real lazyusf2 renderer is
  `scratch/usf2wav` (untracked), and onset fitting is `scratch/zelda-truth.mjs`. Both are offline
  checks only; the app has no lazyusf2, and storing their answers per song would be a per-game table.
- The right song may be absent from the RAM candidates (logo has no state; 100-bananas may load a
  jingle after the state is taken). In that case no pick rule can fix it.
- Rule: "a0 = song at PC X" is per-game knowledge. It is allowed only as a manifest `{kind:"reg"}`
  WHERE-rule, after the generic override rules have been tried. Tag length is a tie-break only.
- Risk: DKR/Banjo/GoldenEye/JFG have song tables and never reach `miniRamSequence`, so keep the pick
  fix in that branch. A "mute reader for every Rare rip" could read Banjo/DKR override words as masks
  and drop channels. A mask is applied only when lazyusf2 renders confirm the channels are silent.
  Every change on those albums is reported and lands as a "(re-capture)" copy. Assert that every
  currently correct song keeps its id.

### Builder steps, in order
1. Dump every state chunk of the 9 minis plus logo (offset, length, value); split CPU state (<0x75C)
   from RDRAM.
2. Decode the saved PC and a0 for each mini, and find the function a0 feeds.
3. Render all 9 minis with lazyusf2 (`scratch/usf2wav`) and render every RAM candidate. Fit onsets;
   for each mini, report the matching candidate or "absent".
4. Check whether the five barrels' lazyusf2 renders differ at all. If they are identical, there is
   nothing to fix.
5. REPORT — no code until the lead approves.
6. Fix generically first (register or override rules in the no-table branch). A manifest reg-rule is
   the fallback, and it needs a warning plus an open-items entry.
7. Build text fixtures from the deciding bytes.
8. Dry-run recapture.mjs on all 5 Rare albums and report the diffs.
9. Apply DK64 in one push, then loudness.
